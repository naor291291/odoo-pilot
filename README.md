# Odoo Pilot - ניסוי בענן

Odoo Community 18, PostgreSQL 16, ניהול פניות ושיבוץ לקבלנים ודיווח תמונות לאישור.
המערכת מיועדת לפיתוח ולניסוי ב־GitHub Codespaces, בלי התקנת Odoo במחשב.

## הפעלה מהדפדפן

1. במאגר לוחצים **Code → Codespaces → Create codespace on main**.
2. ממתינים לבניית סביבת העבודה ולהתקנה הראשונית. ההתקנה נמשכת כמה דקות.
3. בטרמינל של Codespaces מריצים:

   ```bash
   python3 scripts/pilot.py status
   ```

4. כאשר מוצג `Odoo is ready`, מעתיקים את שם המשתמש והסיסמה שנוצרו.
5. בכרטיסיית **Ports** פותחים את פורט **8069** באמצעות סמל הדפדפן.
   משאירים את נראות הפורט **Private**. הכניסה לכתובת מוגנת גם באמצעות חשבון GitHub.
6. נכנסים ל־Odoo עם הפרטים שהוצגו. הממשק מוגדר לעברית ולשעון ישראל.

אם עדיין לא מוכן:

```bash
tail -n 60 .local-data/odoo.log
```

## הגשה, אישור והחזרה לתיקון

1. פותחים את אפליקציית פרויקטים, את **עבודות שטח - פיילוט** ואת משימת הניסיון.
2. בלשונית **דיווח מהשטח** מעלים תמונת לפני ותמונת אחרי.
3. לוחצים **הגשת עבודה לאישור**. ללא שתי תמונות ההגשה נחסמת.
4. העבודה עוברת ל־**ממתין לאישור** והתמונות ננעלות. היא עדיין אינה מסומנת כהושלמה.
5. משתמש עם הרשאת **אישור עבודות שטח** יכול ללחוץ **אישור העבודה**, או להזין
   **סיבת החזרה לתיקון** וללחוץ **החזרה לתיקון**.
6. לאחר החזרה ניתן לעדכן את התמונות ולהגיש מחדש. לאחר אישור העבודה מסומנת Done.

משתמש admin בפיילוט מקבל את הרשאת האישור כדי לאפשר לבדוק את שני הצדדים.
במערכת עם משתמשים נוספים יש להעניק את הקבוצה **אישור עבודות שטח** רק לגורמים המאשרים.
הקבוצה אינה מעניקה גישה לפרויקטים בעצמה; נשמרות הרשאות המשימות הקיימות.
נשמרים מגיש, זמן הגשה, מאשר, זמן אישור ושינויים בציר הפעילות. זו אינה רשומת ביקורת בלתי ניתנת לשינוי בידי מנהל המערכת.

עדכון ישיר של מצב בדיקה או פרטי אישור חסום גם ב־API ובייבוא. אי אפשר לסמן Done לפני אישור.
תמונות שהוגשו או אושרו נעולות גם בשרת. החזרה לתיקון מחייבת סיבה.
שכפול אינו מעתיק תמונות, מצב בדיקה או פרטי אישור. משימות רגילות אינן מושפעות.
התמונות נבדקות כקובצי JPG/PNG/WebP תקינים, עד 12MB ו־50 מגה־פיקסל.

### עדכון Codespace קיים

בטרמינל של הסביבה, מתוך תיקיית המאגר:

```bash
git pull --ff-only
python3 scripts/pilot.py restart
```

לאחר כמה רגעים:

```bash
python3 scripts/pilot.py status
```

לאחר ההפעלה מרעננים את דף Odoo. אין צורך לבנות מחדש את הקונטיינר.
העדכון שומר את מסד הנתונים ואת התמונות. עבודות שסומנו כהושלמו לפני שהיה מנגנון אישור
מועברות להמתנה לבדיקה עם התמונות הקיימות; לא נוצר להן אישור מלאכותי.
אם יש שינויים מקומיים שמונעים git pull, יש לשמור אותם ולבדוק את ההבדלים לפני שממשיכים.

### פניות, שיבוץ וקבלנים

1. לאחר העדכון נכנסים כמנהל ופותחים **עבודות שטח → פניות ושיבוץ**.
2. נוצרה פניית ניסיון **החלפת ברז - דוגמת שיבוץ** בשלב **ממתין לתיאום**.
3. בפנייה בוחרים לקוח וקבלן ומזינים מועד, כתובת ותיאור העבודה לקבלן.
4. לוחצים **שיבוץ ופתיחת משימת שטח**. המעבר מתבצע באמצעות כפתורי ההמשך בלבד.
   גרירת כרטיסים ובחירת סטטוס ישירה במסך בוטלו. השדות נבדקים בשרת, ולפנייה יכולה להיות משימת שטח אחת בלבד.
5. לאחר השיבוץ ממשיכים באותו כרטיס עבודה, כולל תמונות, דיווח ואישור. פרטי השיבוץ
   משתנים מתוך הפנייה ומסונכרנים למשימה המקושרת. החלפת קבלן מבטלת מיד את גישת הקבלן הקודם.
6. הקבלן פותח את אותה כתובת Odoo בחלון דפדפן נפרד, מתחבר בחשבון שלו ונכנס
   ל־`/my/field-work`, או בוחר **עבודות השטח שלי** בדף הפורטל.
7. הקבלן רואה פרטי עבודה, לקוח, טלפון, כתובת ומועד; הוא מעלה ושומר תמונות
   לפני ואחרי ואז מגיש לאישור. הערות CRM פנימיות וסכומי העסקה אינם מוצגים.
8. מנהלת התפעול מאשרת במקטע **דיווח ובדיקת הביצוע** בכרטיס העבודה. הפנייה עוברת אוטומטית ל־**הושלם וממתין לתשלום**.
   החזרה לתיקון מחזירה אותה ל־**בביצוע בשטח** ומאפשרת עדכון ושיבוץ מחדש.

### התקדמות מודרכת בטופס

הטופס כולל כרטיסי לקוח ועבודה, הצעת מחיר ושיבוץ, פס שלבים וסיכום טיפול.
מוצגת רשימת הפרטים החסרים לשלב הבא. אפשר לשמור פנייה חלקית כטיוטה;
לחיצה על המשך תיחסם עד השלמת הפרטים הנדרשים:

| מעבר | נדרש לפני המשך |
| --- | --- |
| פנייה חדשה → ממתין להצעת מחיר | שם עבודה, לקוח, טלפון, כתובת ותיאור עבודה |
| ממתין להצעת מחיר → הצעה נשלחה | פרטי העבודה ומספר הצעת מחיר לאחר שנשלחה ללקוח |
| הצעה נשלחה → ממתין לתיאום | לחיצה מפורשת על אישור הצעה והמשך לתיאום |
| ממתין לתיאום → בביצוע בשטח | כל הפרטים הקודמים, קבלן פעיל ומועד ביצוע |
| בביצוע בשטח → הושלם וממתין לתשלום | אישור דיווח השטח בכרטיס העבודה |

מספר ההצעה מוזן ידנית. הזנתו לבדה אינה מקדמת שלב, מפיקה מסמך במורנינג או שולחת הודעה.
ניתן לחזור שלב אחד באמצעות **חזרה לשלב הקודם**, כל עוד לא נוצרה משימת שטח.
גם עדכון ב־API או בייבוא אינו מאפשר לדלג על שלבים. פניות קיימות נשארות בשלב ובנתונים שלהן;
המשך לשלב הבא מחייב השלמת כל הפרטים הקודמים. אישור והחזרה לתיקון של משימות קיימות נשמרו.

לאחר יצירת משימה לא ניתן להחזיר את הפנייה לשלבים שקדמו לביצוע, למחוק אותה או למחוק
את המשימה. בזמן המתנה לבדיקה ולאחר אישור פרטי השיבוץ נעולים עד החזרה לתיקון.
אפשר לארכב פנייה; עבודתה לא תוצג עוד בפורטל הקבלן.

`python3 scripts/pilot.py status` מציג גם את פרטי שני קבלני הניסיון:
`pilot.contractor.1` ו־`pilot.contractor.2`. הסיסמאות אקראיות ונשמרות מחוץ ל־Git.
פניית הניסיון משויכת מראש לקבלן הראשון וממתינה ללחיצה על כפתור השיבוץ.
אין לשלוח סיסמאות או להעלות אותן למאגר. אין צורך לשתף או לפרסם את פורט Codespaces
לצורך בדיקה: אפשר להשתמש בחלון נפרד המחובר לאותו חשבון GitHub.

### תפקידי משתמשים

- **ניהול ושיבוץ עבודות שטח**: משתמש פנימי לתפעול, עם גישה ל־CRM, לפרויקטים ולאישור דיווחים.
  המשתמש `admin` מקבל תפקיד זה אוטומטית בפיילוט.
- **קבלן - פורטל עבודות שטח**: משתמש פורטל חיצוני; אין לתת לו תפקיד משתמש פנימי.
  גישתו עוברת דרך מסכי הקבלן המוגבלים. גם כתובות ישירות של משימות ותמונות נבדקות מול
  המשתמש המחובר, והמסכים הרגילים של פרויקטים אינם מקנים לו גישה נוספת.
- **אישור עבודות שטח**: התפקיד הקודם נשמר לעבודות התמונות העצמאיות. לאישור עבודה
  המחוברת ל־CRM נדרשת גם הרשאת הניהול והשיבוץ.

ליצירת קבלן אמיתי מנהל המערכת יוצר משתמש פורטל ומוסיף את קבוצת הקבלן בהגדרות המשתמש
במצב מפתח. לא נשלחת הזמנה אוטומטית. בשלב זה אין מסך קליטה עצמי לקבלנים.

הפיילוט משתמש בפרויקט החברה הראשית בלבד. בחירה ושיבוץ לקבלן נעשים ידנית;
בחירה אוטומטית לפי עומס/אזור, קבלה וסירוב, חיוב, גבייה והתחשבנות עדיין אינם כלולים. תמחור ובקרת רווחיות נוספו כמפורט בהמשך.
אישור העבודה אינו סימון שהלקוח שילם. שלב **טופל ושולם** יתווסף עם ניהול התשלומים.

## עצירה, שמירה ועלויות

- עוצרים את ה־Codespace דרך GitHub כשמסיימים לעבוד. עצירתו עוצרת גם את Odoo.
- סביבת העבודה והנתונים נשמרים במהלך חיי אותו Codespace, כולל עצירה וחידוש.
- מחיקת Codespace או מחיקתו האוטומטית עקב חוסר פעילות עלולות למחוק את נתוני הניסוי.
- קוד שנשמר ב־Git נשמר במאגר; תמונות ומסד הנתונים אינם נשמרים בו.
- לחשבון GitHub אישי יש מכסת שימוש חינמית. מחשוב ואחסון נמדדים בנפרד.
  בודקים את המכסה הזמינה ואת מגבלות התקציב בחשבון לפני הפעלה.
  בלי אמצעי תשלום השימוש נחסם כשנגמרת המכסה. עם אמצעי תשלום יש להגדיר תקציב
  שחוסם שימוש נוסף כדי להימנע מחיוב.
- זו סביבת פיתוח ולא אירוח עסקי רציף. אין צורך ב־Cloudpepper במסלול הניסוי הזה.

## סיסמאות ונתוני ניסיון

פרטי כניסה וסיסמת ניהול מסד הנתונים נוצרים אקראית ב־`.local-data`, שמוחרגת מ־Git.
הסיסמה הקבועה בקובץ Compose מיועדת לחיבור הפנימי למסד הניסוי בלבד; פורט מסד הנתונים
אינו מפורסם. אין להפעיל תצורה זו כשרת ייצור או להכניס אליה נתוני לקוחות אמיתיים.
משתמשים פנימיים משתמשים בהרשאות Project ו־CRM. לקבלנים יש פורטל מוגבל ללא הרשאות עריכת משימות ישירות.

## בדיקות

ה־workflow שב־Actions מוגדר להריץ 137 בדיקות אינטגרציה על Odoo ו־PostgreSQL, כולל בדיקות HTTP לפורטל, הפרדת קבלנים, שינוי שיבוץ, אישורים, מעבר נתוני גרסה קודמת, תמחור, הרשאות רווחיות, יבוא מורנינג והפעלה מחדש. בנוסף רצות 15 בדיקות ללקוח ה־API ללא תלות ב־Odoo.
אפשר להריץ אותן גם מהטרמינל של Codespaces:

```bash
python3 scripts/pilot.py test
```

הבדיקות משתמשות במסד נפרד בשם `odoo_pilot_tests` ואינן משנות את מסד הניסיון.
להרצה נקייה חוזרת אפשר למחוק את מסד הבדיקות בלבד לפני הרצת הבדיקות.

## תמחור קבלנים ורווחיות

ב־**עבודות שטח → מחירוני קבלנים**, משתמש בעל הרשאת **בעלים — תמחור ורווחיות עבודות שטח** יכול לערוך מחירון אישי ישירות ברשימת המחירונים הייעודית. ברירות המחדל: 70% עד 500, 65% מעל 500 ועד 1,250, ו־50% מעל 1,250. מדרגה אחת חלה על כל סכום העסקה; 500.01 שייך למדרגה השנייה.

בפנייה מזינים **סכום עסקה לפני מע״מ**, ובעלים מזין **עלות חומרים לפני מע״מ**. סכום העסקה, העלויות וגבולות המדרגות הם בשקלים, כדרישת האפיון; אין המרת מטבע אוטומטית. תשלום הקבלן מחושב על סכום העסקה המלא; הרווח הגולמי הוא סכום העסקה פחות תשלום הקבלן ופחות חומרים. הסכומים מעוגלים לאגורות. שיעור רווח גולמי נמוך מ־35% מציג התראה בצבע ענבר; הפסד צפוי מודגש באדום, בלי לחסום את השיבוץ. סכום אפס מציג בקשה להשלמת הסכום, ללא חילוק באפס.

בבחירת **עבודה ישירה**, בוחרים מבצע פנימי פעיל עם הרשאת עבודות שטח. המשימה משויכת אליו ולא לפורטל קבלן. החישוב כולל חומרים בלבד ואינו כולל שכר עבודה או הוצאות עקיפות. גם עבודה ישירה מחייבת דיווח תמונות ואישור.

אחוזי המחירון נשמרים בעת השיבוץ. שינוי מחירון הקבלן משפיע על שיבוצים עתידיים בלבד. שינוי קבלן או סוג ביצוע במשימה פתוחה מרענן את האחוזים השמורים. מרגע הגשה לאישור נחסמים גם שינויי סכומים, עד החזרה לתיקון.

פרטי רווחיות, עלות חומרים ואחוזי מחירון מוגנים ברמת שדות השרת, מעבר להסתרתם במסך. הם אינם מתועדים בהודעות המשותפות של הפנייה ואינם נשלחים לפורטל. מנהלת תפעול יכולה לעדכן סכום עסקה ולשבץ ללא גישה לחישובי הרווח. חשבון `admin` בפיילוט מקבל את הרשאת הבעלים.

בדיקה ידנית: סכום 1,000, חומרים 100 וקבלן במחירון ברירת המחדל יציגו תשלום צפוי 650, רווח 250 ושיעור רווח 25% עם התראה. בעבודה ישירה אותם סכומים יציגו רווח 900 ושיעור רווח 90%.

זהו אומדן תמחור; שלב זה אינו מפיק חשבוניות, אינו מסמן תשלום ואינו יוצר דוח התחשבנות לקבלן. אינטגרציית Morning ושליחת מסמכים יטופלו בנפרד.


## סביבת עבודה מאוחדת

ב־**עבודות שטח → לטיפול עכשיו** מופיעות פניות שדורשות הכנה, תיאום או בדיקת דיווח. בלוח ובתצוגת הרשימה מוצג הטיפול הבא הנדרש, עם מסננים לשיבוץ, אישור ביצוע ותיקונים.

כל עבודה מנוהלת בכרטיס הפנייה: פרטי לקוח, הצעה, מבצע, מועד, תמונות ואישור. השיבוץ פותח את אותו כרטיס, ומקטע **דיווח ובדיקת הביצוע** מציג את תמונות לפני/אחרי ואת מצב הבדיקה. מנהל יכול להגיש ולאשר מהכרטיס; **החזרה לתיקון** פותחת חלונית שחובה למלא בה סיבה המוצגת לקבלן. מסכי המשימות הוותיקים נשארים זמינים למשימות שאינן מקושרות לפנייה.

בפורטל, **לביצוע / בבדיקה / הסתיימו** מפרידים עבודות פעילות מהיסטוריה. טלפון וכתובת כוללים קישורי חיוג וניווט. לאחר בחירת תמונות מוצגות תצוגות מקדימות והבהרה שטרם נשמרו. **שליחת דיווח לבדיקה** מעלה את הקבצים החדשים ומגישה את הדיווח באותה בקשה; אם חסרים פרטי חובה לדיווח או קובץ אינו תקין, הבקשה כולה מתבטלת. **שמירה והמשך מאוחר יותר** מאפשרת לשמור תמונה אחת במהלך העבודה. אישור הגשה מוצג לאחר תגובת השרת בלבד.

שפה חזותית משותפת חלה על כרטיס העבודה, חלונית התיקון, המחירונים והפורטל: טקסט קריא יותר, תוויות ברורות, פעולות מגע מרווחות, מיקוד מקלדת ומצבי דיווח בטקסט. מד האחוזים המדומה הוסר מהטופס; פס השלבים נשאר. ההערות הפנימיות מתקפלות ומחירוני הקבלנים מוצגים ישירות ברשימה ייעודית.


## דיווח ביקור וגלריות תמונות

בפורטל הקבלן בוחרים **תוצאת ביקור**: הושלם, נדרש המשך או לא בוצע. תוצאת ברירת המחדל היא הושלם, ואפשר לשנותה לפני ההגשה. לביקור שהושלם חובה להזין סיכום קצר ולצרף לפחות תמונה אחת לפני ותמונה אחת אחרי. בביקור שלא הושלם חובה להסביר מה מנע השלמה ומה נדרש להמשך; תמונות וסיכום הביצוע הם רשות. הערות נוספות הן רשות בכל דיווח.

בכל אזור אפשר לשמור עד 5 תמונות, כולל התמונה הראשונה שכבר נשמרה בגרסאות קודמות. בחירה נוספת מוסיפה תמונות, ואפשר להסיר תמונה חדשה או לסמן תמונה שמורה להסרה בשמירה הבאה. להחלפה באזור מלא מסמנים תמונה שמורה להסרה ואז בוחרים חדשה. לחיצה על תמונה פותחת תצוגה מוגדלת. המגבלה, סוג הקובץ, גודלו והרזולוציה נאכפים בשרת גם ללא JavaScript. השרת שומר תמונות בפורמט מעובד עד 1920×1920, עד 12MB לקובץ קלט ו־50 מגה־פיקסל.

**שמירה והמשך מאוחר יותר** שומרת דיווח חלקי, תמונות והסרות בלי להגיש. **שליחת דיווח לבדיקה** שומרת את הכול ומגישה באותה עסקה; שגיאה מבטלת גם הסרות ועדכוני טקסט, והטקסט שהוזן מוצג שוב בטופס לתיקון. בבקשה שנכשלה צריך לבחור מחדש קבצים חדשים.

דיווח שלא הושלם מופיע ב־**לטיפול עכשיו** עם הסימון **ביקור שלא הושלם — נדרש טיפול**. אי אפשר לאשר אותו כהשלמת עבודה. **החזרה להמשך טיפול** מבקשת הנחיה לקבלן ופותחת את הדיווח והשיבוץ לתיאום מחדש; הפנייה נשארת בשלב **בביצוע בשטח**. לאחר הביקור הבא הקבלן מעדכן את התוצאה והדיווח ומגיש שוב. תוצאת הביקור, הסיכום וההערות מתועדים בציר הפעילות; התמונות בגלריות הן התיעוד הנוכחי ואינן ארכיון נפרד לכל ביקור.

איש קשר, דירה/קומה והוראות כניסה מוזנים בכרטיס העבודה ומוצגים לקבלן כשיש נתונים. מועד הביצוע מוצג לפי אזור הזמן של המשתמש, ללא שניות. כל שדות הדיווח והתמונות ננעלים בזמן בדיקה ולאחר אישור; גישה לתמונות בפורטל נבדקת מול השיבוץ הנוכחי בכל בקשה.

## יבוא לקוחות וקישור מסמכי מורנינג

החיבור הוא לקריאה בלבד: חיפוש ושליפת לקוחות ומסמכים קיימים, ללא הפקת מסמכים, שינוי נתונים במורנינג, שליחה ללקוחות או סנכרון רקע. ההזנה הידנית נשארת זמינה גם בלי הגדרת חיבור, כשהחיבור מושבת ובזמן תקלה.

### הגדרת Sandbox

1. יוצרים חשבון ב־[סביבת הבדיקות של מורנינג](https://auth.sandbox.d.greeninvoice.co.il/). לפי [המדריך הרשמי](https://www.greeninvoice.co.il/help-center/generating-api-key/), מגדירים עסק פיקטיבי ומינוי Best פיקטיבי לצורך מפתחות בדיקה; אין צורך לשדרג מנוי אמיתי בשביל בדיקות אלה.
2. באודו נכנסים כמנהל מערכת אל **עבודות שטח → הגדרת חיבור מורנינג**, יוצרים חיבור לחברה הנכונה ומשאירים את הסביבה **Sandbox**.
3. מזינים את מזהה המפתח ואת הסוד של סביבת הבדיקות. אין להכניס מפתחות לקוד, לקבצי Git או להודעות. הסוד נשמר במסד הנתונים עם הרשאת מנהל מערכת בלבד; הוא מוסתר בטופס ואינו נשלח למשתמשי תפעול או לפורטל.
4. לוחצים **בדיקת חיבור — קריאה בלבד**. לאחר שהבדיקה עוברת מפעילים **החיבור פעיל** ושומרים.
5. יוצרים לקוח ומסמכי דמו במורנינג Sandbox, ובודקים את היבוא באודו. החיבור הראשוני כבוי; הקוד אינו יוצר חשבון מורנינג ואינו כולל מפתחות.

לחשבון העסק נדרש מסלול Best ומעלה ומפתחות נפרדים. לאחר קישור לקוחות, החברה, הסביבה ומזהה המפתח נעולים כדי שלא לערבב מזהים משני עסקים או מסביבת בדיקה וייצור. החלפת הסוד של אותו מפתח והשבתת החיבור נשארות אפשריות. העברת נתוני בדיקה לייצור אינה נכללת בשלב זה; יש להגדיר סביבת ייצור נקייה.

### שימוש בכרטיס העבודה

- **בחירת לקוח ממורנינג** פותחת חיפוש לפי שם עם עמודים של 25 תוצאות. בוחרים במפורש לקוח באודו לקישור, או מנקים את השדה ליצירת לקוח חדש. לקוח שכבר יובא ממוחזר לפי מזהה מורנינג; אין מיזוג אוטומטי לפי שם או טלפון. רק פרטים ריקים מתמלאים; כתובת ביצוע, מידע קיים ונתוני תמחור אינם נדרסים. כתובת החיוב מיובאת לכרטיס הלקוח, לא לכתובת העבודה.
- **קישור מסמך ממורנינג** מציג מסמכים של הלקוח המקושר בלבד, לפי סוג ומספר אופציונלי. אפשר לקשר הצעת מחיר, חשבון עסקה, חשבונית מס, חשבונית מס/קבלה או קבלה. מזהה המסמך נשלף שוב מהשרת בעת הבחירה, ונשמרים מספר, תאריך, סוג, מצב, מטבע וסכומים. מסמך יכול להיות מקושר לעבודה אחת בלבד; פיצול חשבונית בין כמה עבודות אינו כלול.
- הצעת מחיר תקינה משלימה את מספר ההצעה רק אם השדה ריק והעבודה אינה נעולה. קישור מסמך אינו מתקדם שלב, אינו מסמן תשלום ואינו משנה את סכום העסקה.
- **עדכון סכום העסקה** הוא פעולה מפורשת עם אישור, על בסיס הסכום ללא מע״מ שבצילום הנתונים האחרון (`amount - vat`, כולל השפעת הנחה ועיגול במסמך). הפעולה זמינה להצעה/חשבונית בשקלים, בסכום חיובי וללא ביטול. קבלה לבדה אינה משנה מחיר עסקה. נעילת סכומים בזמן בדיקה ולאחר אישור ביצוע נשמרת. יש לרענן מסמך לפני הסתמכות על שינויים שבוצעו במורנינג.
- **רענון** מעדכן רק את צילום נתוני המסמך. תקלה משאירה את הנתונים הקודמים ותאריך העדכון מוצג. מצב ״סגור״ או ״סומן ידנית כסגור״ במורנינג אינו הוכחת תשלום. ביטול מסמך מודגש ואינו משנה את שלב העבודה אוטומטית.
- **פתיחת מסמך** מבקשת קישור HTTPS עדכני ממורנינג ופותחת אותו בחלון חדש. בשלב זה נשמר קישור לוגי למסמך, לא עותק PDF מקומי ולא ארכיון מסמכים.
- **הסרת קישור** מסירה רק את השיוך באודו, ללא מחיקת המקור במורנינג. שינוי לקוח או חברה בעבודה עם מסמכים מקושרים מחייב הסרת הקישורים תחילה.

קבלני הפורטל אינם מקבלים גישה לחיבור, למפתחות, לחיפוש לקוחות או למסמכים. חיבור ונתונים מקושרים מוגבלים לחברות המותרות למשתמש. הבדיקות משתמשות בתשובות מדומות ואינן פונות לחשבון אמיתי; מעבר מול Sandbox חי מחייב מפתחות של המשתמש ובדיקה נפרדת.

המימוש מבוסס על [תיעוד ה־API הרשמי](https://developers.morning.co/api) ועל `docs/openapi.bundled.json`, גרסה 2.0.0, שנבדקו ב־30.10.2026. ההזדהות משתמשת ב־OAuth `client_credentials` ובשדה `accessToken`; אין שימוש בנתיב ההזדהות הישן. כתובות השרת קבועות לפי הסביבה, קריאות מוגבלות בזמן ובגודל תשובה, והעברות לכתובות אחרות חסומות כדי לא להעביר מפתחות או אסימונים לשרת אחר.
